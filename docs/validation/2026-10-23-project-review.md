# PS5 Input Bridge 全面评审

评审日期：2026-10-23（Asia/Shanghai）。范围：当前工作区，包括未提交的 Chiaki 导入功能；检查 Core、WPF、原生输入线程、libchiaki 反馈补丁、导入导出、构建发布、测试和调优脚本。未按历史开发者归因。

整体判断：现有分层、DPAPI 账户保护、会话串行化、取消/退出处理有可保留的基础。优化优先级应当是输入正确性、错误恢复和数据安全，然后完善日常使用，再根据真实测量调整性能。当前本机采样性能已经接近配置目标；继续缩短轮询间隔的收益需要端到端证据。

本次没有修改应用、原生补丁或现有测试源码，也没有更新发行目录。新增本报告及 `artifacts/review-2026-10-23/` 下的离线复现材料；执行构建会刷新被 Git 忽略的构建产物。没有读取用户真实账户文件、连接真实 PS5，或运行系统调优脚本。

## Findings：建议先修的问题

P1 表示优先处理的可靠性缺陷，P2 表示需要安排修复的问题。离线接收模型能够确认发送内容和本地状态错误，不能证明真实 PS5 固件的全部处理行为。

### F1 · P1 · 同时释放超过 8 个控件会丢失部分释放事件

- 位置：`native/patches/chiaki/lib/src/feedbacksender.c:149`，尤其 154–155 行的数量截断，以及 244 行提前更新历史状态。
- 触发：依次按住 7 个数字按键及 L2/R2，再一次性归零，例如设备掉线后发送 neutral。之前每个按下事件已经分别成功送出。
- 原因：发送器只发送最近的 8 个控件；未发送的释放被当成已处理。后续 2/8/24 ms 补发和关闭补发都复用同一份缺少释放事件的数据，因此不能补齐。
- 证据：直接编译当前补丁，使用项目已有接收模型复现：释放前 `held=9`，归零、等待补发并关闭后 `held=1`。没有模拟网络丢包也能出现。
- 修复：保证一次状态变化产生的所有控件事件都能发送；如果协议限制单包数量，就拆包并维护待发队列。不要直接假设扩大包长一定被真实主机支持。
- 测试盲区：`native/tests/test_feedback_sender.c:203` 同时按下 18 个控件再释放，只检查最终是否归零，没有检查 18 个按下是否都送达。按下和释放丢掉相同控件时，测试仍通过。应增加“逐个按住，再统一释放”的回归。

### F2 · P1 · 网络发送失败仍被上层记为成功

- 位置：`native/patches/chiaki/lib/src/feedbacksender.c:132`、145、241–259；`native/src/ps5bridge.c:375`。固定上游的 `lib/src/session.c:339` 也未转交 sender 的返回值。
- 原因：摇杆发送失败仅写日志，历史包发送直接忽略返回码；状态快照随后照常前移，公开 setter 返回成功。上层输入线程因此更新“上次成功状态”，失败计数和重试机制无法反映实际 UDP 发送错误。
- 证据：让实际 sender 调用的模拟传输返回 `CHIAKI_ERR_NETWORK=6`，setter 仍返回 `0`。耗尽定时补发、恢复传输后，再提交相同输入，新增历史包为 `0`。
- 影响：本地发送错误期间的按下/释放可能丢失；界面提交次数和诊断信息也会误导排障。这和 UDP 已发送后在网络中丢失是两个不同场景。
- 修复：在 session → sender → transport 整条链上传递错误，明确“采集状态”“待发送状态”“发送成功状态”，并在输入不变时仍重试尚未送达的变化。用真实 sender 的故障注入测试验证，而不仅在输入线程测试中替换整个 session setter。

### F3 · P2 · 同时运行两个实例会覆盖账户新增结果

- 位置：`src/Ps5Bridge.Core/AccountStore.cs:9`、61；`src/Ps5Bridge.App/MainWindow.xaml.cs:52`、83–84；`src/Ps5Bridge.App/App.xaml.cs:5`。
- 原因：账户锁仅属于单个 `AccountStore` 实例，窗口加载后保留自己的列表，保存时覆盖整个文件。应用没有单实例约束，也没有文件版本冲突检测。
- 证据：两个独立 store 同时读取空列表；A 添加账户 A 后，B 根据自己的旧快照添加账户 B。最终文件只剩 B，两个保存调用都成功。使用临时路径和合成凭据完成复现。
- 修复：此项目最直接的方案是同一 Windows 用户只运行一个实例。若确实支持多实例，需要在跨进程锁内重新读取、合并或检测版本冲突；只锁住最后的写文件步骤不够。

### F4 · P2 · HID 序号不是稳定身份，热插拔可能换错手柄

- 位置：`native/src/ps5bridge.c:180`、226、420–424；`src/Ps5Bridge.App/MainWindow.xaml.cs:401`、415–417。
- 触发：存在 A、B 两只 HID 手柄，当前序号为 4、5。拔掉 A 后，B 的序号变成 4。原本选择 A 的会话下一次打开序号 4 时可能接管 B；原本选择 B 的序号 5 则可能持续报告找不到手柄。
- 原因：按设备路径排序只保证同一集合下顺序稳定，不能保证设备集合变化后序号稳定。UI 也只保存 Index。
- 修复：在托管和原生之间传递稳定 DeviceId，连接时绑定具体设备路径/容器标识；设备消失先释放输入，恢复时只匹配原设备。UI 刷新保留同一个身份。
- 验证状态：代码路径确认；本次没有进行实体手柄插拔测试。

### F5 · P2 · 关键回归测试没有进入构建发布门禁

- 位置：`tools/build-native.ps1:17`；`tools/publish.ps1:12`；`native/CMakeLists.txt:100` 附近的独立测试目标。
- 现状：构建脚本只执行 `ps5bridge-tests.exe` 和 `test_abi.py`，遗漏 `ps5bridge-feedback-tests.exe`、`ps5bridge-input-tests.exe`、`test_bootstrap.py`；发布脚本没有执行 34 项 WPF 检查。仓库没有已跟踪的 CI 工作流。
- 影响：最关键的丢包补发、输入边沿、采样间隔回归可以在发布时被跳过；测试文件存在不代表发布已验证。
- 修复：提供统一校验入口，使用 CTest 注册原生功能测试，并在发布前执行托管、原生和 UI 检查。采样时序阈值测试容易受运行机负载影响，应与确定性的功能测试分开，在受控环境执行性能门禁。
- 同时修正 F1 的假通过测试，以及 `tests/Ps5Bridge.Tests/NativeBackendTests.cs:99`：其默认样例 Target=1000，本身不满足原生只接受 1000100 的条件，不能单独证明 ControllerIndex=42 被拒绝。

### F6 · P2 · 修改依赖版本后，缓存仍可能使用旧源码

- 位置：`native/scripts/bootstrap.py:42`，以及 `download()` 对现有无哈希文件的复用逻辑。
- 原因：只要 `.bridge-source-ready` 存在就跳过，不比较其中 URL 与当前固定版本；源码压缩包又只以依赖名称命名，清掉标记后也可能继续解压旧缓存。
- 证据：临时目录写入 old-commit 标记，调用 `source()` 请求 new-commit，函数直接成功返回，标记仍是 old-commit。
- 修复：以 commit/version/SHA-256 作为缓存身份，验证标记和压缩包内容，变化时重新准备源码。对下载的源码和 protoc 补充哈希校验；本次没有确认这些原生依赖是否存在具体可利用 CVE。

### F7 · P2 · 系统调优备份不覆盖第二张网卡或后续环境

- 位置：`tools/tune-windows.ps1:71` 和恢复分支 43–57 行。
- 触发：先对网卡 A 执行调优，再通过 `-AdapterName` 调优 B；备份文件已经存在，因此 B 的原值没有保存。`-Restore` 只处理第一份备份中的 A。新增 USB 集线器或改变电源计划也有相似情况。
- 修复：按网卡 GUID、电源计划 GUID、设备身份保存原值；对于尚未备份的目标，先补齐备份再修改。检查 `powercfg` 的退出码，恢复失败应明确报告。
- 验证状态：静态确认。未运行此脚本，没有修改网卡、电源计划或 USB 设置。

### F8 · P2 · 账户文件导入没有大小上限，密码派生阻塞 UI

- 位置：`src/Ps5Bridge.App/MainWindow.xaml.cs:194`；`src/Ps5Bridge.Core/AccountPortableBundle.cs:46`、51、56–58。
- 原因：任意文件直接全部读入，随后复制密文、分配等量明文；不像本地 AccountStore 和 Chiaki 导入那样先限制大小。攻击者可控制头部的迭代次数，上限为 1000 万；耗时计算在 WPF 线程执行。
- 证据：把合成小文件的迭代数改成 1000 万，本机在最终拒绝文件前同步计算约 960.5 ms。超大文件的额外内存占用可从分配路径确认，未进行耗尽内存测试。
- 修复：给文件长度、账户数量、KDF 参数设定与格式版本匹配的边界；在后台执行密码派生，显示忙状态。派生密钥字节数组也应使用 `finally` 显式清理。不要将取消按钮描述成能立即中断一个不支持取消的 KDF 调用。

## 体验、性能和结构优化

以下属于下一阶段建设建议，和上面的缺陷修复分别安排。

| 方向 | 当前情况 | 建议与验收方式 |
| --- | --- | --- |
| 账户日常管理 | 没有编辑地址、改名、删除入口；同一注册密钥重导入会被跳过 | 优先增加编辑 Host、改名、删除。DHCP 地址变化应复用现有配对凭据，并明确提示重连；测试地址更新后原密钥保持一致 |
| 配置即时生效 | 更换手柄或采样档都会经 `Options_SelectionChanged` 重建整个 PS5 会话 | 账户不变时使用已有原生 setter 更新；HID 模式下禁用无效的采样选项，避免无意义断线。手柄身份修复先于热切换 |
| 启动体验 | 每次恢复默认账户选择、采样档和 Back 映射；入口较多 | 保存用户偏好；默认展示连接和账户选择，把导入导出放到清晰的账户管理区域。增加设备不兼容/被占用的具体提示 |
| 性能策略 | 原生线程独立采样，变更直发；100 μs 活跃档忙等 | 保持 500 μs 默认。极限档按实际手柄报告周期和负载提供选择，不进一步无条件提高线程优先级或忙等频率 |
| 指标可信度 | 只有平均/最大提交耗时；计时起点不包含采样等待、USB/网络/PS5；握手期间 setter 也可能只缓存状态 | 分开统计采样间隔、实际发送耗时、发送失败、重试、P95/P99 和 CPU。只有 transport 实际接受数据才增加发送成功数 |
| 端到端验证 | 本次验证均为本机离线；反馈测试的接收器是假设模型 | 用真实 PS5 验证短按、组合键、双指触摸、拔线、切账户、断网重连、丢包和长时间运行；抓取仅该 PS5 的流量确认媒体状态，用高速录像/硬件测量比较 HDMI 响应 |
| 日志诊断 | `pb_create()` 将 chiaki 日志级别设为 0；界面也未显示已有的输入故障统计 | 增加可导出的有限长度诊断日志、会话标识、发送失败计数。过滤配对密钥/PIN/令牌；采样热路径使用有界缓冲，避免同步写盘 |
| 模块维护 | Core/App/native 边界合理；主窗口约 479 行、原生文件约 883 行且承担多项职责 | 分拆账户操作服务、设备发现、HID 解析、输入调度、会话生命周期；UI 可逐步引入 ViewModel。保持现有架构，按修复涉及范围逐步提取 |
| 验证设计 | 输入测试替换 session 提交函数，反馈测试替换传输，各自通过不保证端到端错误传播 | 增加穿过真实 session/sender 的故障测试；对 HID 解析补短报文/异常报文边界，对热插拔补稳定身份测试，对触摸事件补丢包及乱序场景 |
| 发行与依赖 | 固定依赖版本但缓存身份不足；无 global.json；原生补丁采用整文件替换 | 先修 F6，再固定 SDK、生成依赖清单/哈希/构建版本，保存补丁基线差异；评估 .NET LTS 与原生依赖升级，验证 ABI、协议兼容性及对应源码包 |
| 文档准确性 | `native/README.md` 同时出现 HID 支持和旧版“不支持原生 HID”的表述，极限档说明也与新空闲策略不一致 | 统一支持矩阵、采样/USB/端到端延迟定义；宣传中的微秒指标附测试环境和原始证据。整张网卡的流量差值只能辅助判断媒体，不能证明是否停传 |

本次 NuGet 漏洞查询在 nuget.org 当前数据下没有报告测试工程及其传递依赖的已知漏洞。这不涵盖静态编译的 mbedTLS、curl、libevent、chiaki 等原生依赖，也不等于整体安全审计通过。

## 待实机确认的事项

没有证据证明目前端到端延迟低于硬件转换器，也没有证据证明 PS5 已停止全部媒体流量。反馈包格式/序列号/重发语义需要与真实主机验证，尤其在调整事件打包之后。蓝牙、第三方 DS 模式手柄和多 HID 设备热插拔也需要相应硬件。

## 建议执行顺序

1. 修复 F1/F2 的输入发送与释放逻辑，同时补能失败的回归测试并完成实机验证。
2. 修复 F3/F4 的账户覆盖和设备身份问题，把 F5 的遗漏测试接入统一门禁。
3. 处理 F6/F7/F8 的依赖缓存、调优备份和导入边界；完善账户编辑和配置即时生效。
4. 建立 P95/P99、实际发送失败率和端到端测量，再决定是否值得继续优化极限采样。

五维评估：正确性 Concern；安全 Concern（数据覆盖、输入边界、构建完整性）；性能 Concern（极限档成本、UI 同步工作、测量覆盖）；可维护性 Concern（缓存、模块职责、文档）；验证 Concern（现有测试通过，但新复现证实有覆盖缺口）。
