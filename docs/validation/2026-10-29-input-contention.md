# 1.0.5-latency.1：输入统计隔离与延迟诊断

## 结论

本轮确认了一个可消除的阻塞来源：详细统计窗口的读取不再占用输入锁，统计锁忙时输入线程跳过发布。关闭 XInput 详细统计也减少了每次采样的工作，但正常场景平均延迟基本持平，未证明真实操作明显变快。因此交付独立测试版，保留原 1.0.4 和已有 1.1.0 包；不将本版宣称为已经实机验证的低延迟正式版。

当前工作区包含此前未提交的 1.0.4 修复，基线不是 Git HEAD。改动前先完整冻结匹配源码/头文件/静态库/DLL和哈希到 `artifacts/latency-contention/baseline`，然后构建并运行原生回归。基线 DLL SHA-256：`6403b34e1ee8ef5329823d731dabe2bdef0c7a85aed2dd2b8a1adab1cf0cb808`。

## 实现与行为边界

- XInput 详细耗时和分位数窗口默认关闭，`PS5BRIDGE_XINPUT_TIMING=1` 恢复。读取进度、原始状态、失败计数、读取超时保护、100μs 采样时钟和卡轴保护保留；显示用读取耗时换算移至 getter。HID 默认仍不做详细计时。
- 独立统计快照约每100ms发布；输入侧 `TryEnterCriticalSection` 失败就跳过。时序 getter 不获取输入锁，排序仍在锁外；状态/健康等其它小 getter 仍有短临界区。停止前先提交中立，再发布最终快照。设备/会话变化用原子版本使旧时序失效；失败计数独立保留。
- `PS5BRIDGE_DIAGNOSTICS=1` 增加可选输入锁、反馈锁、发送调用和补发持锁记录。每阶段最近4096条加全程次数/累计/最大值，在内存采集、相关线程结束后写CSV。默认不分配诊断数组、不调用新增诊断时钟；CSV不含输入值、地址或凭据。
- 公共 ABI 仍为6，必须随测试版附带匹配 DLL。协议、按键映射、同步首发、补发时机、加密算法、停止释放顺序均不变。没有证据支持继续改写补发调度，因此未做该项。

## XInput 对照

工具 `tools/latency-contention/` 使用同一模拟8K输入、生产100μs线程、真实加密与UDP环回。三种版本为冻结基线、候选详细计时开启、候选默认关闭。每工况三组轮换次序，每轮预热1秒、测量6秒。实际WPF工况为小型WPF面板/DispatcherTimer调用生产getter，不是完整正式UI。后台负载、CPU频率和系统调度没有严格控制。

初轮27次、1,296,000个源时隙，全部前台提交失败为0。表中P99是每轮P99的平均；跳过状态是未被轮询观察到的模拟源状态，不是网络丢包。

| 工况 | 版本 | 生成→本地提交平均 / P99（μs） | 跳过源状态 / 144000 |
|---|---|---:|---:|
| 每500ms原生UI读取 | 基线 | 61.290 / 115.233 | 292 |
| 每500ms原生UI读取 | 候选，计时开启 | 61.230 / 114.433 | 167 |
| 每500ms原生UI读取 | 候选，默认 | 61.276 / 115.267 | 119 |
| 人工统计持锁暂停 | 基线 | 61.291 / 115.533 | 741 |
| 人工统计持锁暂停 | 候选，计时开启 | 61.519 / 116.500 | 327 |
| 人工统计持锁暂停 | 候选，默认 | 61.318 / 115.233 | 152 |
| 实际WPF面板 | 基线 | 61.957 / 117.267 | 159 |
| 实际WPF面板 | 候选，计时开启 | 62.047 / 118.067 | 258 |
| 实际WPF面板 | 候选，默认 | 61.821 / 116.167 | 198 |

人工工况每500ms在UI统计getter拿锁后 `Sleep(2)`，实际暂停时长也保留；不代表真实UI必然如此。计时开启候选发生197次发布尝试，其中17次锁忙而跳过，证实非阻塞分支被执行。默认版不积累时序窗口，通常不需周期发布。强回归测试另持有统计锁超过200ms，验证输入持续发送及最终释放。

不利结果也保留：初轮WPF默认版跳过源状态159→198，三组分别66→100、54→55、39→43；采样间隔P99为106.833→108.833μs。人工压力的计时开启候选还出现一次约8.37ms提交尖峰。不能宣称消除了调度卡顿或所有指标都改善。

针对正常WPF差异追加了三组基线/默认版对照（共6轮）：平均61.690→61.640μs，P99 114.800→113.633μs，跳过19→18/144000，前台提交失败仍为0。两批所有结果均保留；复测没有稳定复现跳过量退化，也没有建立明显提速证据。不能只挑其中一批作为总体结论。

基线对“候选计时开启”包含统计快照、新诊断关闭分支、健康耗时换算位置等整个基础路径变化，不是严格快照单变量；候选计时开启/关闭比较才隔离统计开关。其收益不足以证明毫秒级改善。

证据：`artifacts/latency-contention/comparison-final/`、`wpf-confirmation/`，含raw CSV、每轮JSON、哈希、编译命令及WPF实际tick记录；独立审查见 [基准复核](2026-10-29-contention-benchmark-review.md)。

## HID 对照与复测

复用 `tools/latency-hid/` 的受控报告+真实发送路径；新增私有头文件也纳入构建哈希。初轮18次，针对8K异常再复测12次，所有前台提交失败为0。

| 工况 | 生成→提交平均μs，基线→候选 | FIFO丢报告，基线→候选 | 缺失模拟按键边沿，基线→候选 |
|---|---:|---:|---:|
| 首轮1K连续，9000报告/版 | 29.632→29.797 | 0→0 | 0→0 |
| 首轮8K连续，72000报告/版 | 21.169→21.052 | 64→127 | 68→128 |
| 首轮8K人工积压，72000报告/版 | 29.539→29.842 | 108→155 | 132→198 |
| 复测8K连续，72000报告/版 | 19.979→19.920 | 0→0 | 0→0 |
| 复测8K人工积压，72000报告/版 | 27.972→28.370 | 110→128 | 138→160 |

首轮8K连续候选的一轮模拟生产者曾晚调度约11.96ms；复测连续输入两版均无丢失。人工积压每100ms注入 `Sleep(1)`，实际暂停并不等长：复测基线三轮均值约1.290/1.365/1.227ms，候选约1.298/1.157/1.486ms，故不能把溢出差值直接归因于输入代码。候选在两批人工积压总数仍更差，不作“可靠性提升”声明。该实验的8格FIFO及满时丢旧报告是测试模型，不是对真实Windows HID驱动策略的断言。

本轮没有解决线程暂停导致的积压，也不再尝试曾无稳定收益的双缓冲。证据：`artifacts/latency-contention/hid-comparison/` 和 `hid-confirmation/`。

## 诊断实跑

另运行6秒连续8K模拟变化，加1秒预热，开启诊断、保留真实加密UDP环回及500ms原生UI读取。全程零提交失败，正常退出导出input和feedback CSV。

| 阶段 | 全程平均μs | 全程最大μs |
|---|---:|---:|
| XInput提交前输入锁等待 | 0.028 | 9.8 |
| 反馈锁等待 | 0.023 | 5.9 |
| 摇杆包发送调用 | 5.377 | 85.2 |
| 按键历史包发送调用 | 4.652 | 50.0 |

发送调用包括该路径的加密与Winsock提交，不是独立加密算法时间，也不是NIC实际发出或PS5接收时间。连续输入不断推迟补发，后台真正补发样本很少，不能据此排除真实停顿/释放场景的补发争用。HID诊断起点在报告取出后，不能测USB到达或OS唤醒延迟。最近4096样本的分位数只代表尾部窗口，全程mean/max来自独立累计。证据：`artifacts/latency-contention/diagnostic-run/`。
