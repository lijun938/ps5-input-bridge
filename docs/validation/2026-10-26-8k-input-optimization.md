# 2026-10-26 8K XInput 发送路径优化

本轮实现减少补发通知、加密临时分配与重复初始化、采样诊断重复加锁。采样档位仍为 100/500/1000 μs；首次输入同步发送、补发与失败恢复、公共 ABI 6 和控制映射保持原有语义。应用版本更新为 1.0.2。

## 代码变化

- 反馈 worker 在条件等待前记录截止时间；只有新的最早截止时间更早时才通知。持续输入推迟补发时不再逐包唤醒 worker。通知标记与截止时间由原有 mutex 保护，停止仍无条件唤醒。
- GKCrypt 对对齐后不超过 256 字节的密钥流使用栈缓冲，较大包仍分配内存。每实例持有 MbedTLS GMAC context，按实际密钥周期重新设置 key；旧包临时换回旧 key 后，后续新包会重新安装正确的 key。每包仍重置 IV/消息状态，未缓存密文。
- 删除 `gcm_starts` 后紧接 `crypt_and_tag` 所造成的重复消息初始化。后台 AES 密钥流生成继续使用独立上下文。
- Takion 历史包 payload 不超过 256 字节时使用栈缓冲，大包保持 heap 路径；补齐包头长度加法的溢出检查。原有网络错误继续向上返回。
- 采样私有函数依赖调用方已经持有的 context 锁，移除每次诊断更新的递归加锁。独立审查逐一确认 XInput、HID、看门狗和离线释放调用方仍持锁。没有移动发送到异步队列，也没有扩大无锁访问范围。
- Bootstrap 除原错误返回补丁外，应用 `chiaki-low-latency.json`；GKCrypt 源码和头文件作为完整替换文件保存在补丁目录。

## 专项验证

测试先在改前实现上暴露额外开销，再验证优化实现：

| 验证 | 改前 | 改后 |
|---|---:|---:|
| 321 次连续状态变化触发的通知 | 321 | 1 |
| 同一测试的 worker 等待次数 | 321 | 20–21 |
| 63 次同一密钥周期内小包加密的临时 malloc | 63 | 0 |
| 同一测试的 GMAC setkey / 多余 starts | 各 63 | 各 0 |

以上分配计数针对被包装的代码路径；不表示程序整体从不分配内存。密钥周期切换仍需重新设置密钥。

- 唤醒专项 3/3：每个变化仍在返回前发送；从长等待转到短补发可及时恢复丢失的首包。
- 加密专项：416 组独立 AES/GMAC 参考向量全部一致，覆盖两个实例、后台密钥流、未对齐/零长/256 与 257 字节边界、大包、密钥周期边界和乱序旧密钥。初始化分配、密钥设置、线程创建及发送失败的恢复/资源清理通过。
- 历史包专项：8 种大小的真实环回 UDP 密文、认证码、序号和 key position 与预期一致；只有 3 个大包使用 heap，分配失败、大小溢出、网络错误均通过。
- 原有反馈回归 13/13、采样线程回归 30/30、原生 ABI/转换/HID 自检、真实加密 Winsock 错误恢复全部通过。
- Python ABI/生命周期/补丁验证 12/12，包括从固定上游源码压缩包应用所有补丁两次并验证完全一致。
- 托管测试 84/84、WPF 离线界面检查 85/85 通过。
- 新增测试和项目自身代码采用 `-Wall -Wextra -Werror`；测试包含的上游源码局部抑制既有诊断。上游其他库仍有原有警告，构建日志保留这些输出。

## 8K 对照方法

工具：`tools/latency-8k/run.py` 与 `benchmark_body.h`。改前采样源码、Chiaki 头文件、生成配置和静态库保存在 `artifacts/latency-8k/baseline`；每版使用配套的头文件与静态库。生成 manifest 记录源文件、共享依赖、可执行文件和原始 CSV 的 SHA-256，跑完再次核对构建输入未变化。

模拟 XInput 状态按独立 QPC 时间轴每 125 μs 更新一次，实际 `input_worker` 用 100 μs 档轮询。晚采样只取得最新状态，不补造跳过的历史状态。真实执行 session → feedback sender → AES/GMAC → Winsock UDP 环回发送，并运行看门狗、补发线程和正式配置的 256 KiB 后台密钥流缓存（local index 2）。

两种工况各 3 对，改前/改后交替，共 12 轮。每轮预热 1 秒、测量 6 秒；共生成 576,000 个测量时隙。摇杆工况每时隙改变双摇杆并保持 L1；混合工况额外每 10 ms 切换 L1/R1，且每时隙改变两枚扳机，以增加历史包负载。

“读取”时间戳是模拟 provider 选择最新状态的时刻，包含其后的少量记录开销，并非真实 USB 时间戳，也不完全等于界面统计的采集起点。“提交”截止于真实同步 session 调用成功返回，不表示 PS5 已接收。均值及分位数是三轮统计量的平均值，未将原始样本池化。

## 本机结果（μs）

| 工况/指标 | 改前 | 改后 |
|---|---:|---:|
| 摇杆：读取 → 提交平均 | 7.037 | 5.792 |
| 摇杆：读取 → 提交 P99 | 19.533 | 17.533 |
| 混合：读取 → 提交平均 | 11.817 | 10.074 |
| 混合：读取 → 提交 P99 | 28.500 | 23.967 |
| 摇杆：生成 → 提交平均 | 57.176 | 55.920 |
| 摇杆：生成 → 提交 P99 | 106.533 | 105.200 |
| 混合：生成 → 提交平均 | 61.961 | 60.194 |
| 混合：生成 → 提交 P99 | 112.000 | 109.767 |

读取至提交的平均耗时在这组测试中分别减少约 17.7% / 14.7%，绝对减少约 1.2 / 1.7 μs。采样平均周期仍为约 100.39–100.40 μs。采样线程 CPU 仍约为一个核心的 99.7%；未计算接收、反馈、看门狗和密钥流线程的整体 CPU 收益。

全部轮次前台提交失败为 0。每版每工况各 144,000 个源时隙：摇杆跳过时隙为 23 → 4；混合为 6 → 5。它们是未被轮询观察到的源状态，不是 UDP 丢包。系统负载、温度、频率和调度未严格控制，改前单次约 1.47 ms 的采样尖峰明显影响极值；不能据此声称消除了毫秒级卡顿或保证漏采率改善。

没有使用真实 Xbox 手柄、USB 驱动、局域网或 PS5，也未运行 WPF 界面参与性能测量。本结果支持本机代码路径开销降低，不构成真实 8K 更新率或端到端控制延迟证明。
