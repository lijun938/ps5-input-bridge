# 2026-10-29 输入统计与锁竞争基准独立复核

## 复核范围

读取 `artifacts/latency-contention/comparison-final/` 的 `runs.json`、`summary.json`、`report.md` 和九份 WPF `.ui.json`，独立重算计数及聚合指标。没有运行新基准、编译或修改生产代码。为避免干扰同时进行的 HID 测量，本轮没有再次扫描所有原始 CSV；原始 CSV 的时间戳、观察/提交计数和构建哈希检查由本次基准 runner 完成并通过。

27 轮覆盖 native getter、人工锁内暂停、实际 WPF 小面板三个场景，每个场景三个版本、每版三轮；每轮预热一秒，测量六秒。输入为模拟 8 kHz 状态源，采样使用真实 100 μs XInput worker，随后走真实反馈发送、加密及 UDP 环回。它不包含实际手柄、USB 驱动、局域网、PS5 接收/处理或电视显示。

## 可以支持的结论

**快照隔离确实让输入线程在统计读取锁被人为暂停时继续工作；当前数据没有证明正常使用的平均操作延迟有可感知改善，也不能声称消除了所有尖峰。**

| 场景 | baseline 生成→本地提交平均（μs） | current-default 平均（μs） | baseline 跳过源状态 | current-default 跳过源状态 |
|---|---:|---:|---:|---:|
| native getter | 61.290 | 61.276 | 292 / 144000 | 119 / 144000 |
| 人工锁内暂停 | 61.291 | 61.318 | 741 / 144000 | 152 / 144000 |
| 实际 WPF 小面板 | 61.957 | 61.821 | 159 / 144000 | 198 / 144000 |

正常 WPF 场景中，默认版平均减少约 **0.136 μs（0.000136 ms）**。三对均有很小的平均下降，但只有三轮、后台调度/CPU 状态未严格控制，不能据此保证稳定硬件收益。native 场景平均差仅约 0.014 μs，人工暂停场景默认版平均反而增加约 0.027 μs。平均值没有形成显著、全面的提升证据。

人工暂停场景下，默认版跳过源状态从 741 降到 152；三对分别为 `262→80`、`269→51`、`210→21`，方向一致。详细统计仍开启的 current-timing 合计跳过 327，也少于 baseline。这里的暂停是测试明确注入的 `Sleep(2)`，不是观测到正式界面每 500 ms 卡顿两毫秒。

current-timing 的人工暂停场景记录 **197 次快照发布尝试、17 次锁忙而跳过**。三轮分别是 `73/13`、`60/0`、`64/4`，每轮恰有 60 次成功发布，与 100 ms 发布节奏及六秒测量窗口相符。17 是失败尝试数，不是 17 次不同的 UI 暂停，更不是丢失 17 个手柄输入。它证实了生产 `TryEnterCriticalSection` 的跳过分支在这组基准中实际执行。current-default 关闭详细统计，正常无新增统计窗口，因此测量期内发布计数为零是预期行为。

## 必须保留的不利结果

- **WPF 默认版的跳过源状态三对均更多**：`66→100`、`54→55`、`39→43`，合计 `159→198`。其采样间隔 P99 也从 106.833 增至 108.833 μs。这个小样本不足以证明生产性能退化，但不能被平均延迟微降掩盖，也不能写成“所有指标无回归”。
- WPF 场景 current-timing 合计跳过 258，生成→提交平均 62.047 μs，均未优于 baseline。
- 人工暂停场景 current-timing 有一次 **8.373 ms** 的生成→提交尖峰，几乎全部落在同步提交调用内；默认版各场景仍存在毫秒级最大值。诊断关闭的本轮无法把它归因到某把锁、网卡或具体线程，因此不得宣称已消除卡顿。
- 100 μs 忙等仍约占一个 CPU 核心。各轮 CPU 百分比差异受调度和计时粒度影响，不能拿它承诺降低整机 CPU 占用。

“跳过源状态”指 8 kHz 最新状态模型中，在两次读取之间被覆盖、没有被应用采样到的模拟时隙。它**不是 UDP 丢包数、实际漏按键数或 PS5 未收到的包数**。因为迟到的读取会取得最新状态，观察到的生成→提交延迟仍可能很小；采样空档与跳过数必须和延迟均值一起看。

## 计数与配置一致性

独立检查通过：

- 共 27 轮、1,296,000 个测量源时隙；每轮 `observed + skipped = generated`。
- 每轮 `submission_count = observed_slots`，所有前台提交失败及缓冲溢出均为零。零提交失败只表示本地调用成功，不证明 PS5 已收到。
- baseline、current-timing 的最终详细计时样本数均大于零；current-default 全为零，确认环境开关实际生效。
- `summary.json` 的计数、平均值、各分位数及最大值均与三轮 `runs.json` 重算一致；分位数是每轮分位数的平均，不是把所有样本合并后的分位数。
- 九轮 WPF sidecar 均返回成功、无异常，每轮实际调用 14 次 getter，与 native JSON 中的 UI 计数一致；记录的 DispatcherTimer 间隔约为 496.8–503.2 ms。
- 人工暂停三版本均记录 39 次暂停（含预热）。实际暂停总时长 baseline 88.405 ms、current-timing 84.406 ms、current-default 84.359 ms，并非完全相等，不能把差值全算作软件收益。

## 单项归因边界及交付建议

baseline→current-timing 包含完整基础路径变化：独立统计快照、禁用诊断时的分支、健康统计转换移到 getter 等，不能把所有差异单独归因于快照。current-timing→current-default 才是同实现的详细统计开关比较；其生成→提交平均差在 native、人工暂停、WPF 中分别约为 `+0.046`、`−0.201`、`−0.226 μs`，仍是很小且依工况变化的结果。

实际 WPF 工况是小型真实 WPF 面板、真实 DispatcherTimer 和生产 getter；不是完整正式程序的账户列表、全部控件和设备枚举负载。测试也没有模拟真实设备驱动的所有行为。

适合对用户的表述是：**已隔离详细延迟统计窗口的读取锁，人工压力测试验证输入能够继续；正常平均延迟基本持平，仍需真实手柄与 PS5 A/B。** 状态及健康信息 getter 仍会短暂读取输入共用锁，所以不能表述成“界面完全不再与输入争锁”。本轮可以交付测试版本和可复现诊断，不能据此宣称“明显提速”“降低了若干毫秒”或“所有延迟指标均改善”。
